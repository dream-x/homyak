# Постмортем: 44 часа без доставки в Telegram (6–8 августа 2026)

## Коротко

Умер апстрим HTTP-прокси, через который бот ходит в Telegram Bot API. Сбор и обработка новостей
работали всё это время нормально — встала только доставка: пуши, канал и ответы бота. Обнаружено
вручную пользователем, все три монитора молчали.

| | |
|---|---|
| Начало | 6 августа, ~16:24 (последний успешный пуш) |
| Обнаружено | 8 августа, ~02:10 — пользователем, не мониторингом |
| Починено | 8 августа, 02:24 |
| Длительность | ~34 часа до обнаружения, ~44 до полного восстановления |
| Потери | 0 новостей (собраны и обработаны), ~2 суток пушей не доставлено вовремя |

## Что произошло

`gost` на VM (`-L http://:8118 -F socks5://…@109.120.139.237:34069`) форвардил в внешний
SOCKS5-узел. Узел перестал отвечать (`dial tcp 109.120.139.237:34069: i/o timeout`).

Сам контейнер при этом продолжал работать и слушать порт 8118 — он просто не мог никуда
дозвониться. Бот получал `ProxyError: 503` на каждый `getUpdates` и ушёл в бесконечный
ретрай-цикл: **5526 попыток** к моменту обнаружения.

Что при этом продолжало работать:
- сбор новостей (37/час) — tscraper ходит в Telegram другим путём, через SSH-SOCKS туннель `:1080`;
- весь пайплайн обработки — LLM, скоринг, вика;
- веб (`/lenta`, `/search`, `/trends`).

То есть система выглядела «живой» по всем внутренним признакам, но пользователь не получал ничего.

## Почему мониторинг не поймал

Три независимых монитора, и все три смотрели мимо:

| Монитор | Что проверял | Почему молчал |
|---|---|---|
| **Gatus** `bot-proxy gost (:8118)` | `[CONNECTED] == true` — TCP-коннект к порту | Порт был жив: `gost` слушал. Проверялся сокет, а не проход трафика. |
| **Сторож пайплайна** (в боте) | обработано ли что-то за 2ч при непустой очереди | Обработка шла штатно — сбой был не в пайплайне. |
| **`node_down`** (Grafana) | `up{job=~"node.*"}` | Хост VM жив. |

Корень: **проверялась живость компонента, а не сквозная работа сценария.** Прокси, который слушает
порт и никуда не ходит, для такой проверки неотличим от исправного.

## Что сделано

1. **Апстрим заменён.** Пользователь выдал новые реквизиты SOCKS5 (`185.21.12.196:39206`).
   `gost` пересоздан на них; сквозная проверка `api.telegram.org` через `:8118` → `302`.
   Бот перезапущен: 0 ошибок прокси, пуши и канал пошли.
   Старая команда сохранена в `~/proxy/OLD_ARGS.txt` на VM.

2. **Gatus-проверка переписана на сквозную** — вместо TCP-коннекта делает реальный HTTP-запрос
   к `api.telegram.org` **через** прокси и ждёт `302`:

   ```yaml
   - name: bot-proxy gost (:8118)
     url: "https://api.telegram.org/"
     client:
       proxy-url: "http://192.168.140.20:8118"
     conditions:
       - "[STATUS] == 302"
   ```

   Такой обрыв теперь ловится за минуту. **Не применено**: конфиг обновлён (бэкап рядом), но
   контейнер не перезапущен — на sirius нет прав на `docker.sock` (см. «Открытые вопросы»).

## Диагностическая находка

При проверке нового прокси curl'ом: `socks5://` → таймаут, `socks5h://` → `302`. Разница в том,
где резолвится DNS: локально на VM `api.telegram.org` резолвится в адрес, который не проходит,
а на стороне прокси — нормально. `gost` резолвит на стороне апстрима, поэтому у него всё работает,
но при ручной диагностике curl'ом это выглядит как «прокси не работает». Стоит помнить.

## Уроки

1. **Проверять сценарий, а не компонент.** Живой порт ≠ работающий канал. Это же касается остальных
   проверок: `tg-tunnel (socks5 :1080)`, `galaxy proxy`, `tg-tunnel exit galaxy` в Gatus — все они
   сейчас на `[CONNECTED] == true` и имеют ровно ту же слепоту.
2. **Нужен монитор доставки, а не только обработки.** Сторож смотрит на пайплайн; пуши могут стоять
   при идеально работающем пайплайне. Проверка «последний успешный пуш был больше N часов назад»
   поймала бы это независимо от причины.
3. **Ретрай без алерта — это тишина.** 5526 неудачных попыток подряд не породили ни одного сигнала.
   Счётчик подряд идущих ошибок должен сам становиться поводом для алерта.

## Открытые вопросы

- **Gatus не перезапущен** — нужен `sudo docker restart gatus-gatus-1` на sirius (прав нет).
- **Единая точка отказа**: и Bot API, и MTProto теперь идут через внешние узлы одного класса;
  при этом туннель `:1080` (galaxy) остаётся рабочим резервом для Bot API — переключение делается
  одной командой (`-F socks5://172.17.0.1:1080`), проверено 8 августа.
- **Монитор доставки не реализован** — см. урок 2.
- Апстрим-креды намеренно не в git (инвентарь ссылается на gitignored runbook
  `homelab/homyak-vm/`), но самого runbook в репозитории нет — реквизиты живут только у пользователя.
